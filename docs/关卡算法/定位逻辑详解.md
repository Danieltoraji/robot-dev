# 定位逻辑详解：从核心到边缘

> 本文面向想彻底看懂本仓库“AprilTag 视觉定位”的读者，也适合第一次接触的小白。
> 阅读顺序建议：
> 1. 先看第 1~3 章，搞懂“定位到底在做什么”；
> 2. 再看第 4 章，理解“为什么最简方案会失败”；
> 3. 之后从第 5 章开始，按“核心 → 边缘”一层层看当前算法怎么补上这些失败点。

---

## 0. TL;DR（太长不看）

机器人没有可靠的轮式里程计，只能靠 **拍照 + AprilTag + PnP** 来知道自己在哪、朝向哪。

最简做法是：

```text
拍照 → 识别 AprilTag → 把所有角点丢给 solvePnP → 得到位置和朝向
```

这个做法在“一帧能看到多个不同平面的标签”时基本够用；但在本赛道最常见的是“只看到一面墙/一个标签”，此时 **共面 PnP 存在镜像歧义**，最简做法可能拿到一个重投影误差很小、但物理位置错误的结果。

当前算法是在最简做法外面，一层层加上保护：

```text
核心：PnP 求解
  + 合理性门控          → 拦掉明显离谱的假解
  + 头部偏转补偿        → 转头后把相机朝向换算成机体朝向
  + 头部扫描/身体重试    → 一个方向看不见就换方向看
  + 共面歧义消解        → 解决“两个解都看似合理”的问题
  + 多帧联合定位        → 单帧信息不够时，用多帧几何一致性消歧
  + 帧救援/宽扫/离线标定 → 继续提高成功率和精度
```

**结论**：定位能力必不可少；当前复杂方案不是多余，而是对真机失败模式的分层防御。

## 1. 机器人为什么需要定位

### 1.1 开环动作不可靠

机器人的“前进 5cm”“左转 22°”是动作组，不是精确的编码器位移。实测表明：

| 项目 | 误差 |
|---|---|
| 单次位置残差中位 | 约 2.6~2.9cm |
| 单次位置残差 p95 | 约 6.7~9.1cm |
| 单次航向残差中位 | 约 3~4° |
| 单次航向残差 p95 | 约 14~15° |

连续走几步后，位置和朝向可能偏离几十厘米。赛道里墙离机器人可能只有十几厘米，停靠点误差要求 3cm 左右，所以**不能只靠“我走了几步”来猜自己在哪**。

### 1.2 定位要回答两个问题

1. **我在场地哪个位置？** → `(x, y)`
2. **我朝哪个方向？** → 单位向量 `(dx, dy)`

本仓库用 `current_position` 和 `current_orientation` 保存这两个量。

> 代码细节：`current_position` 实际保存的是“相机光心投影到地面的 x,y”，也就是机器人用于导航的参考点；它不是物理重心，但整套导航阈值和安全余量都按这个参考点标定，所以逻辑自洽。

## 2. 先搞懂几个基础概念

### 2.1 世界坐标 / 机器人坐标 / 相机坐标

- **世界坐标**：场地固定的坐标系，单位 cm。例如 `tag_poses` 里每个标签角点存的是世界坐标。
- **机器人/机体坐标**：以机器人为原点的坐标系。前进方向通常作为 y 或某个轴。
- **相机坐标**：以相机光心为原点的坐标系。

定位算法要做的事，就是通过“已知世界坐标的标签”和“照片里标签的像素位置”，反推出相机在世界坐标中的位置和朝向。

### 2.2 相机成像：3D 点怎么变成 2D 像素

一个三维点 `P_world` 经过相机位姿（旋转 `R`、平移 `t`）和内参 `K`，会投影到照片上的像素 `p_pixel`：

```text
P_camera = R * P_world + t
p_pixel  = K * P_camera（再做归一化和畸变校正）
```

相机内参 `K` 是固定的，已经标定好放在 `camera_config.py`。

### 2.3 PnP 是什么

PnP（Perspective-n-Point）是已知：

- 一组 3D 世界点；
- 它们在照片上的 2D 像素点；

反求：

- 相机在世界中的旋转 `R` 和平移 `t`。

OpenCV 的 `cv2.solvePnP()` 就是干这个的。

### 2.4 AprilTag 给了我们什么

AprilTag 是一种二维码式标签，每个标签有唯一 ID。算法可以从照片里检测到：

- 标签 ID；
- 标签四个角点的像素坐标。

仓库里已经知道每个标签在世界坐标下的四个角点位置（`tag_poses`），所以：

```text
3D 世界点 = tag_poses[id]
2D 像素点 = 检测到的角点
```

把两者丢给 PnP，就能算出相机在世界中的位姿。

## 3. 最简定位流程（先看这个）

### 3.1 流程

```text
拍照
  → AprilTag 检测
  → 收集所有已知标签的 3D 角点和 2D 像素角点
  → cv2.solvePnP()
  → 得到相机位置和朝向
  → 取 x,y 作为机器人位置，取朝向的 x,y 分量作为机器人朝向
```

伪代码：

```python
def locate_simple():
    img = capture_image()
    tags = detect_apriltag(img)

    objlist = []   # 3D 世界点
    imglist = []   # 2D 像素点
    for tag in tags:
        if tag.id not in tag_poses:
            continue
        objlist += tag_poses[tag.id]
        imglist += tag.corners

    ok, rvec, tvec = cv2.solvePnP(objlist, imglist, K, D)
    R = cv2.Rodrigues(rvec)[0]
    cam_pos = -R.T @ tvec          # 相机在世界中的位置
    cam_ori = R.T @ [0, 0, 1]      # 相机光轴方向
    return cam_pos[:2], cam_ori[:2]
```

### 3.2 这种最简方案什么时候能工作

当一帧里能看到**两个以上不同平面的标签**时，例如同时看到“墙上的标签”和“地面上的标签”，点集不再是共面的，PnP 解通常是唯一的，最简方案基本够用。

## 4. 为什么最简方案会失败

### 4.1 问题根源：共面点集存在两个解

当所有 3D 点都落在**同一个平面**上时（例如只看到一面墙，或只看到一个 AprilTag），PnP 会存在两个数学解：

1. 真实位姿；
2. 一个“镜像/翻转”的假位姿。

这两个解投影到图像上几乎一样，重投影误差都很小。

> 关键点：**真实世界只有一个物理合理位姿，但仅靠单帧共面角点 + 重投影误差，无法区分哪一个才是物理解。**

这就是单目视觉里著名的 **planar PnP ambiguity**。

### 4.2 普通 solvePnP 只返回一个解，而且可能返回错的那个

`cv2.solvePnP(..., SOLVEPNP_ITERATIVE)` 只返回一个结果。它返回正确支还是镜像支，取决于初值和数值过程，不是“自动选择物理解”。

仓库实测记录：

> 在“两个解都通过门控”的共面帧里，普通 ITERATIVE 有约 1/4 概率落到错误支。

### 4.3 简单门控拦不住所有假解

你可能会想：那加一个“位置必须在场地内、高度要合理、朝向要水平”的判断不就行了？

这些门控能拦掉**明显离谱**的镜像解，但拦不掉另一类：

- 错误解也在场地内；
- 高度也正常；
- 朝向也接近水平；
- 重投影误差也很小。

它只是位置偏了几厘米到二三十厘米，看起来仍然“物理上合理”。

### 4.4 没有使用运动先验

正确支和错误支通常差得很远。如果知道上一次定位位置，以及这期间动作大概走了多远，就能判断：

> 哪个候选更符合“我从上一个位置走动作后应该到的地方”。

最简方案没有利用这个信息，所以无法消歧。

### 4.5 没有使用多帧一致性

单帧平面观测信息不足，但如果机器人不动、头部转几个角度拍多帧：

- 正确支在所有帧之间互相一致；
- 错误支在帧之间会互相矛盾。

多帧联合能利用这个矛盾淘汰错误支，最简方案没有这一步。

### 4.6 总结失败链

```text
只看到一面墙/一个标签
  → 共面歧义
  → 普通 solvePnP 随机返回一个支
  → 门控不够强，错误支也通过
  → 把错误位置当成真位置
  → 导航按错误位置走
  → 撞墙/出界/到达不了目标点
```

## 5. 当前定位算法总览（分层图）

当前算法在 `core/robot_core.py` 里，是一层一层叠起来的“洋葱”：

```text
┌─────────────────────────────────────────────────────────────┐
│ 第 9 层  离线标定：survey_field / multiview_extrinsics       │
│ 第 8 层  身体转动重试 locate_with_retry                      │
│ 第 7 层  宽扫档（第二档转头）                                 │
│ 第 6 层  多帧联合定位 _locate_joint                          │
│ 第 5 层  帧救援：逐标签剔除                                  │
│ 第 4 层  共面歧义消解：IPPE + 期望选支                        │
│ 第 3 层  头部扫描：回正 → 右转 → 左转                        │
│ 第 2 层  头部偏转补偿 compensate_head_offset                 │
│ 第 1 层  合理性门控 pnp_pose_problems                        │
│ 第 0 层  拍照 + AprilTag + solvePnP                         │
└─────────────────────────────────────────────────────────────┘
```

其中：

- **第 0~3 层**是“没有就不能闭环”的核心；
- **第 4~8 层**是“针对真机失败模式的鲁棒/兜底”；
- **第 9 层**是离线校准，不参与每帧运算，但决定精度上限。

## 6. 第 0 层：拍照 + AprilTag + PnP

### 6.1 代码入口

- `RobotState.capture_image()`：用 `fswebcam` 拍一张照片。
- `RobotState.detect_apriltag()`：检测 `tag36h11` 家族的 AprilTag。
- `solve_pnp_pose()`：把 3D/2D 点交给 `cv2.solvePnP()`。

### 6.2 角点顺序约定

`tag_poses` 中每个标签的四个角点顺序统一为：

```text
左上 → 右上 → 右下 → 左下
```

而 AprilTag 库返回的 `corners` 顺序经真机验证也是这个顺序，所以代码里：

```python
TAG_CORNER_PERM = np.array([0, 1, 2, 3])
```

这看起来像没做事，但它是一个**显式承诺**：防止未来换库/换版本后角点顺序悄悄变化。

### 6.3 PnP 结果

`cv2.solvePnP()` 返回旋转向量 `rvec` 和平移向量 `tvec`，代码进一步转换成：

```text
相机在世界中的 3D 位置：pos_3d
相机光轴在世界中的方向：ori_3d
```

然后取：

```text
current_position = pos_3d[:2]
current_orientation = ori_3d[:2]
```

## 7. 第 1 层：合理性门控（第一道安全网）

### 7.1 为什么需要

`solvePnP` 对错误角点顺序、镜像分支也可能给出“重投影误差很小”的结果。所以不能只要 PnP 返回成功就接受。

### 7.2 检查什么

代码在 `pnp_pose_problems()` 中检查：

| 检查项 | 含义 | 常量 |
|---|---|---|
| 相机位置在场地范围内 | x,y 不能跑出场地 | `PNP_FIELD_MIN/MAX` |
| 相机高度合理 | z 不能太低或太高 | `PNP_CAM_Z_MIN/MAX` |
| 相机朝向接近水平 | z 分量不能太大 | `PNP_ORI_Z_MAX` |
| 相机不是垂直朝下/上 | XY 分量不能太小 | `PNP_ORI_XY_MIN` |
| 重投影误差足够小 | 点和投影点平均误差不能太大 | `PNP_REPROJ_ERR_MAX_PX` 等 |

### 7.3 多标签阈值

- 单标签帧：重投影误差阈值较严（约 2px）；
- 多标签帧：因为标签世界坐标之间存在手工测量残差，阈值放宽到约 11px。

只要有任何一项不通过，本次单帧定位就判失败，交给上层重试，**绝不输出一个可疑位姿**。

## 8. 第 2 层：头部偏转补偿

### 8.1 问题

头部舵机可以左右转头拍照。`solvePnP` 求出的是**相机朝向**，不是**机器人机体朝向**。

如果头部向右转了 40°，相机朝右前方看，但机器人身体可能还是朝正前方。直接把相机朝向当作机体朝向，决策就会偏。

### 8.2 做法

代码在转头定位成功后调用：

```python
compensate_head_offset(head_pulse)
```

它根据头部脉宽换算转头角度 `theta`，然后把相机朝向绕机体旋转回去：

```text
机体朝向 = R(-theta) * 相机朝向
```

### 8.3 注意

这里补偿的是**朝向**。`current_position` 在单帧成功时保存的是相机光心投影位置，不是物理重心；这个语义在整套导航中是统一的。

## 9. 第 3 层：头部扫描（一个方向看不见就换方向）

### 9.1 流程

`locate_with_scan()` 的顺序是：

```text
1. 头部回正拍照
2. 成功？→ 返回
3. 失败？→ 头部右转拍照
4. 成功？→ 补偿头部偏转 → 回正 → 返回
5. 失败？→ 头部左转拍照
6. 成功？→ 补偿头部偏转 → 回正 → 返回
7. 全失败 → 进入更后面的兜底
```

### 9.2 为什么需要转头

机器人的摄像头视野有限，某个方向可能：

- 看不到任何 AprilTag；
- 只看到一个标签且歧义严重；
- 标签被墙挡住。

转头可以扩大可视范围，提高定位成功率。

## 10. 第 4 层：共面歧义消解（本算法最核心的“补丁”）

### 10.1 什么时候进入

`_locate_pose_once()` 检测完标签后，会判断当前帧里的标签是否**共面**。

判断方法很简单：看所有标签角点的世界坐标中，是否有一个轴几乎不变。

例如：

```text
所有标签都在 x≈45 的墙上 → x 坐标几乎不变 → 共面
所有标签都在地面 z≈0     → z 坐标几乎不变 → 共面
```

### 10.2 共面时怎么做

代码不再使用普通 `solvePnP` 的“只返回一个解”，而是：

```text
用 solvePnPGeneric / IPPE 显式枚举两个候选解
  → 先让合理性门控筛一遍
  → 如果只剩一个，接受它
  → 如果两个都活着，尝试用“期望位置”选一个
  → 如果还不能选，就交给多帧联合定位
```

### 10.3 IPPE：把两个解都找出来

IPPE（Infinitely Polar Plane Estimation）是专门解共面 PnP 的算法，能一次性给出两个解。

普通 `solvePnP` 像是“闭眼抓一个”，IPPE 则是“把两个都摆在桌上，再判断哪个是真的”。

### 10.4 期望选支：用上一次位置来猜

正确支和错误支通常位置差很远。代码保存了：

- 上一次成功定位位置；
- 最近动作的位移预算。

于是可以算每个候选离“期望位置”的距离：

```text
距离更近、且明显比另一个更近 → 选它
两个距离差不多 / 无法判断     → 不冒险，交给多帧联合
```

### 10.5 为什么不能盲目选“更近的那个”

如果定位噪声大，或者上一次位置本身就不可靠，光看“更近”可能选错。所以代码要求：

```text
|dA - dB| > 阈值  且  只有一个候选落在期望半径内
```

才用期望选支。否则不强行选，交给多帧。

## 11. 第 5 层：帧救援（剔除坏标签）

### 11.1 问题

一帧里可能同时看到好几个标签，但其中某个标签：

- 贴歪了；
- 反光导致角点检测差；
- 世界坐标测得不准确。

结果整帧 PnP 重投影误差很大，门控失败。

### 11.2 做法

当多标签帧全集求解失败时，尝试“每次去掉一个标签，重新 PnP”：

```text
尝试 {所有标签}
尝试 {去掉标签 A}
尝试 {去掉标签 B}
尝试 {去掉标签 C}
...
```

如果某个子集能通过门控，就接受这个子集的结果。

### 11.3 限制

不是随便剔除都行：

- 子集至少要 2 个标签；
- 子集必须跨至少 2 个平面，避免又变成共面歧义。

这个机制不是“定位的必要条件”，而是为了**少一次转头/重试，省 2~4 秒**。

## 12. 第 6 层：多帧联合定位（单帧不够，多帧来凑）

### 12.1 为什么需要多帧

单帧共面观测信息不足，尤其当两个候选都通过门控、期望也选不出来时。

但如果机器人不动、头部转到不同角度拍多帧：

- 头部转角是已知的；
- 相机光心会因偏心而绕一个小圆弧移动；
- 正确位姿必须同时解释所有帧的观测；
- 错误支通常无法让所有帧都一致。

所以多帧联合可以用“全局一致性”淘汰错误支。

### 12.2 数学模型

`multiview_pose.py` 用一个 8 参数向量描述机器人/相机系统：

```text
[x_B, y_B, phi_deg, e_x, e_y, z_c, pitch_deg, k_head]
 机体x  机体y  机体朝向  光心偏心   相机高度  俯仰角  头转系数
```

其中：

- `x_B, y_B, phi_deg` 是要求的机器人位姿；
- `e_x, e_y` 是相机光心相对机体的偏心；
- `z_c` 是相机高度；
- `pitch_deg` 是相机俯仰角；
- `k_head` 是实际转头角度与舵机标称角度的比例系数。

这些外参由离线标定得到，存在 `archive/result/multiview_extrinsics.json`。

### 12.3 运行时只解 3 个自由度

离线标定已经把外参固定住，运行时只需要联合求解：

```text
x_B, y_B, phi_deg
```

也就是机器人的平面位置和朝向。

### 12.4 留一法

多帧联合也不是“一次就信”。代码会尝试：

```text
全集
去掉第 1 帧
去掉第 2 帧
去掉第 3 帧
...
```

然后取“能通过门控且重投影 RMS 最小”的组合。这样即使某一帧是坏帧，也不会把整体解带偏。

### 12.5 什么时候触发

在 `locate_with_scan()` 里，多帧联合发生在：

- 常规三档单帧都失败，但至少缓存了 2 帧角点；
- 宽扫后仍有 2 帧以上角点。

---

## 13. 第 7 层：宽扫档（覆盖更偏的角度）

### 13.1 为什么需要

常规右转/左转档位覆盖约 ±40.5°，但某些朝向（例如出口走廊朝东时）需要的标签可能在约 70~80° 方向，常规档看不到。

所以代码增加了第二档宽扫：

```text
HEAD_WIDE_RIGHT ≈ -63°
HEAD_WIDE_LEFT  ≈ +63°
```

### 13.2 定位

宽扫帧也走“单帧优先，失败后并入联合缓存”的流程。

如果当前固定路线不走出口段，这一层可能很少触发，但它是覆盖死区的保险。

---

## 14. 第 8 层：身体转动重试

### 14.1 流程

`locate_with_retry()` 在头部扫描全部失败后，不再原地放弃，而是：

```text
for 第 1..5 次尝试:
    if locate_with_scan(): 成功返回
    身体左转一次（约 22°）
```

### 14.2 为什么同向连转

历史上有过“左右交替转”的版本，但左右交替净旋转约为 0，转 5 次后朝向几乎没变，死区还是死区。

改成同向连转后，每次身体都增加累计转角，能扫到原本在侧后方的标签。定位成功后，由上层导航再转回目标朝向。

### 14.3 上限

最多重试 5 次，防止在某些位置死循环。

---

## 15. 边缘：位置连续性守卫（当前只是观测）

代码里有一个 `_accept_position()`，它看起来像在“守卫位置跳变”，但当前实现是：

```text
如果新位置和上次位置差得超过“动作预算 + 裕度”
  → 只打印一行日志
  → 不拒绝、不拦截
  → 照常接受新位置
```

为什么这样？历史复盘发现：坏读数可能出现在“跳变的另一侧”，如果简单拒绝跳变，可能把正确解也拒了，让机器人在错误位置上继续走，比跳变更危险。

所以现在它只是**事后诊断工具**，不是运行必需逻辑。

---

## 16. 第 9 层：离线标定（决定精度上限）

### 16.1 为什么需要离线标定

- `tag_poses` 最初是手工尺量的，标签之间相对误差可能有约 1cm；
- 相机光心相对机体有偏心；
- 头部偏航轴可能不严格竖直；
- 舵机标称角度和实际转角有比例偏差。

这些都会让 PnP 产生系统误差，尤其是多标签帧。

### 16.2 相关工具

| 工具 | 作用 |
|---|---|
| `tools/field_calib/collect_multi_view.py` | 真机采集多站位、多转头帧数据 |
| `tools/field_calib/survey_field.py` | 多站位 Bundle Adjustment，精化标签坐标和外参 |
| `tools/field_calib/diag_kinematics.py` | 验证“光心偏心 + 头转”运动模型是否自洽 |
| `tools/field_calib/head_compensation_check.py` | 真机验证转头定位补偿是否有效 |

最终产物包括：

```text
archive/result/tag_poses_refined.json          # 精化后的标签世界坐标
archive/result/multiview_extrinsics.json       # 相机外参（偏心/高度/俯仰/头转系数等）
```

### 16.3 运行时如何使用

`RobotState` 初始化时读取 `multiview_extrinsics.json`；如果文件不存在，就退化为“光心=机体中心”的缺省外参并打印警告。

## 17. 定位在导航循环里的位置

定位不是单独跑一次就结束，而是被 `navigate_to_target()` 反复调用：

```text
while True:
    定位 locate_with_retry()
    检查当前离墙距离
    计算离目标还有多远
    如果朝向偏了 → 转向
    如果位置还没到 → 走一步 / 批量直行
    继续循环，直到到达目标点
```

```python
# levels/goodluck.py 中的调用：
if not state.locate_with_retry():
    print("无法定位，导航失败。")
    return False
```

所以定位算法的好坏，直接决定导航是否能在错误累积前及时纠正。

## 19. FAQ

### 19.1 既然真实世界只有一个物理解，为什么还要 IPPE/多帧联合？

因为“真实物理解”只有一个，但“单帧共面观测在数学上”对应两个重投影都很小的候选。不把两个候选都枚举出来，就无法做后续判断。

### 19.2 能只用普通 solvePnP 吗？

在“每帧都保证看到多个平面标签”时可以。当前赛道无法保证，所以不行。

### 19.3 能只保留门控，不要歧义消解吗？

不能完全放心。门控能拦掉大量明显假解，但存在“错误解也满足门控”的情况。歧义消解正是处理这些漏网之鱼。

### 19.4 多帧联合定位是不是很慢？

它只在单帧全部失败、且有 2 帧以上角点时触发，不是每次定位都跑。正常情况走“头部回正单帧成功”的快路径。

### 19.5 我想简化代码，应该删哪些？

- 位置连续性守卫当前不拦截，可以认为不是运行必需；
- 旧 `solve_pnp()` 方法如果没人调用，可以清理；
- 帧救援、宽扫、多帧联合是鲁棒性增强，删之前建议先做 A/B 真机测试。

---

## 20. 总结

当前定位算法可以理解成一句话：

> **用最可靠的单帧 PnP 做快路径；一旦遇到“单帧不可信”或“单帧信息不足”，就用门控、歧义消解、多帧联合、转头重试一层层补救。**

它不是为复杂而复杂，而是为了应对以下真实问题：

1. 动作开环误差大 → 必须外部定位；
2. 只看到一面墙/一个标签 → 共面歧义；
3. 普通 solvePnP 可能选错支 → 用 IPPE 枚举；
4. 门控可能拦不住 → 用期望位置/多帧一致性；
5. 一个方向看不见 → 转头、宽扫、身体转；
6. 坏标签污染整帧 → 剔除救援；
7. 标签坐标和外参不准 → 离线 Bundle Adjustment 标定。

把这七层都理解后，再看 `core/robot_core.py`、`core/multiview_pose.py`、`core/camera_config.py`，就会清楚每一段代码是在防哪一个坑。
