### 1.2.1 ★ 根因查明：到达判据的阈值在这个几何下**不可达**（本轮新增，真值位姿逐帧对齐）

把仿真**真值位姿**与逐帧色占比对齐打印（`ng_press_diag.py`）：

| seed | 面板 | 目标格心 | 峰值占比 | 压到终点时的占比 | 终点离格心 | 比值 |
|---|---|---|---|---|---|---|
| 11 | 1 | (16.7, 50.0) | 0.1323 @ (25.5,35.0) | 0.0889 @ (19.0,47.3) | **3.5cm** | **0.672** |
| 7 | 2 | (16.7, 50.0) | 0.1350 @ (20.4,35.1) | 0.0904 @ (17.8,46.1) | **4.1cm** | **0.670** |

⇒ **机器人其实已经站到格心上了（3.5~4.1cm），但到达判据判不出来**：

1. `VIS_ARRIVE_PRESS_MAX_CM = 45` 在机器人正好走到格心时耗尽 ⇒ 退出循环；
2. 退出前的回落只到峰值的 **0.67**，而 `VIS_COLOR_DROP_FRAC = 0.55` 要求 **< 0.55**
   ⇒ 证据门不放行；
3. 兜底的"死推到位"判据（`|fwd| ≤ 6cm` 且 `|lat| ≤ 5cm`）**也没接住**
   ⇒ 本格记未确认。

**几何原因**：`PITCH_DOWN=1040` 的实际俯角是 41.4°+18.5°=**59.9°**，画幅下沿对应地面
**3.5cm**（不是注释里写的 16cm）⇒ 站在 28cm 面板中心时，面板**远侧那一半仍然在画面里**
（约 14cm×28cm）⇒ 占比只能降到峰值的 ~0.67，**永远到不了 0.55**。
"色块出现→消失"这个模型在 PITCH_DOWN 这套几何下**不成立**。

⇒ 这就是用户方案没触及、但真正吃掉到达率的那个洞。处置见 §2.6。

### 1.3 分区律"蓝档"是死代码（决定性）

`tools/_tmp_recalib2.py` 的 A/B 装置是**有效**的：把 `VIS_ZONE_ROT_NEAR` 从 0.35 扫到 9.0，
`_zone_of` 返回 `'lat'` 的次数是 **63 / 67 / 11 / 0**，而四项指标（42/56、1684、1076、逐动作计数）
**逐位相同**。矛盾的解释是：

- 全部 63 次 `'lat'` 都来自 `_approach_visual:2351`；`_align_visual` **一次都没返回过 `'lat'`**。
- 2351 判到 `'lat'` → 调 `_align_visual` → 进函数后**第一个判据在 2280 行**：
  `if abs(yaw) <= VIS_ALIGN_TOL_DEG or (... _zone_of(...) == "move")`。
  `|yaw| = 7.8~9.2° ≤ 12°` ⇒ 第一个析取项立刻成立 ⇒ `return`（"已对准"）。
- 于是 2288~2303 的横移档 `_act(left_move/right_move)` **在数学上不可达**：
  要走到 2291 必须 `|yaw| > 12°`，而那时 `_zone_of` 只会返回 `'rot'`。
- 实测佐证：装了 `_act` 探针后 seed 3 的 15 次横移**全部**发生在 `ARRIVE1..7`
  （`VIS_ARRIVE_LAT_VIA_SIDESTEP` 那条路），stdout 里 `[对准] 平移档` **0 行**。

**这不是"分区律没用"，是"分区律没执行"。** commit `e43a803` 只修好了 APPROACH 段的
**咨询**，ALIGN 段（2280/2291）没修。把 2280 也接到 `_zone_of` 后立刻可测：

| 臂（4 种子、实测原语） | 到达 | 拍照 | 动作 |

| ZONE_OFF（二值基线） | 25/28 | 875 | 578 |

| ZONE_ON + 2280 也接 `_zone_of`（无迟滞、无收尾禁转） | **24/28** | **991** | **597** |

### 1.4 MAP-ANCHOR 的数学可行性（我自己先验证机制）

### 1.5 ★ 但 MAP-ANCHOR 的**可用性**很窄（决定它不能当主机制）

每格开始时在 `HEAD_CENTER + PITCH_NAV` 拍一帧，数"未裁切且在 map 里"的面板：

| seed | 逐格可用数（panel1..7） | ≥4 的格 |
|---|---|---|
| 3 | 7, 1, 0, 0, 1, 0, 0 | 1/7 |
| 7 | 7, 1, 0, 0, 1, 0, 0 | 1/7 |
| 11 | 7, 0, 1, 0, 1, 0, 0 | 1/7 |
| 21 | 7, 0, 0, 0, 1, 0, 0 | 1/7 |

全帧口径：**≥4 的帧占 9~18%，≥5 的占 3~5%**。
原因有二：① 机器人压到上一格后，邻格距离仅 33cm ⇒ 面板投影像宽 >1600px，
被画幅裁切；② 更近的面板会被检测器的 `MAX_AREA_FRAME_FRAC=0.35` 当"too_big"整块丢弃
（实测多格 `观测0`）。只有**第一格（站在场外）**稳定有 7 个。

> ⚠️ **2026-09-24 更正（对抗性评审逐帧普查否证了②）**：`last_rejected` 在 671 帧里
> **全空**，未裁切面板被漏检 **0/832（0.00%）**，28cm 面板在 20cm 站位时峰值仅占画幅
> **0.286**（<0.35）⇒ `too_big` **从未拦过任何面板**。**唯一主因是画幅裁切**
> （面板-帧普查：裁切 68.1%、出画幅 17.7%、相机后方 14.2%）。
> 另：20cm 处像宽是 **1074px**（非 >1600px）；未裁切上限是 **6**（格 6 恒空），
> 提到"7"是主 agent 的笔误。

> ★ **但可用率是可以抬上去的**（评审实测）：裁切面板仍然贡献它**未被裁掉的四个角点**，
> 那是**精确对应点**。把"未裁切面板质心 + 裁切面板的真实角点"合并成对应集后，
> ≥4 对应的帧占比从 **8.6~18.6% 升到 69.5~81.4%（4.6~9.4 倍）**，且 RANSAC 仍能在
> **91%** 的拟合里给出 <2cm 的位姿（中位 0.00cm、中位 10 个内点）。
> ⇒ MAP-ANCHOR **不必**只是"长距帧机制"；这是下一步最有价值的升级（见 §7.4）。


⇒ **结论：MAP-ANCHOR 是"长距帧的核验/定位器"，不是全程可用机制。**
必须如实写进方案，并且**不允许**在没有实测增益的情况下把它接进控制回路。

### 1.6 评测工具的缺口（用户要求"对仿真器等评测工具作必要的检查"）

| 工具 | 现状 | 缺口 |
|---|---|---|
| `sim/nine_grid_sim.py` | 投影/裁切/头部/俯仰/形变/打滑都真实 | **没有任何同色杂物/假货**；颜色=数字=唯一 ⇒ **两个同色候选在物理上不可能出现**；**无遮挡**（面板共面 z=0，无机体几何） |
| 多种子扫描 | **不存在可复现的入口**；只有 gitignore 的 `tools/_tmp_*.py` | 且 `_tmp_recalib.py` 的 `zone` 参数是死参数（A/A 对照），历史上已造成一次错误结论 |
| 真值集 `tests/fixtures/nine_grid_truth/` | 73 条（68 真/5 假）判据混淆矩阵可用 | ① **没有布局/位姿/相机档位**（grep `cell\|layout\|pose` 0 命中）；② 12 帧里**每帧最多 3 个未裁切不同数字**，0 帧达到 ≥4 ⇒ **锚核验跑不起来**；③ 5 个假货**全部 `clip==1`** ⇒ 无法与"贴边门"区分；④ 假货只在 3/12 帧里 |

⇒ **结论：现有的仿真器与真值集都无法验证"格子核验能否拒绝同色假货"。**
这是本轮必须先补的能力（§3）。

## 2. 完整算法

### 2.1 总览（分层，每层都能单独开关与单独验证）

```
                    ┌───────────────────────────────────────────┐
   layout_scan ───► │ Map = digit→cell（组合信息，= 本方案的锚） │
   （场外预扫）      └───────────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼────────────────────────────┐
        ▼                           ▼                            ▼
  L1 MAP-ANCHOR              L2 候选核验/救援              L3 三档分区决策
  （≥4 未裁切已知格）        （可否被地图解释）            （绿直行/蓝平移/橙旋转）
  解 H → 实测位姿/h          外点 = 违背 map              给 _align_visual / _approach
        │                           │                            │
        └───────────────┬───────────┴────────────────────────────┘
                        ▼
                 L4 消费点：搜索提示 / 离场护栏 / 遥测
```

### 2.2 L1 MAP-ANCHOR（新，纯函数，可单测）

```
map_anchor(obs, digit_cell, pitch, head) -> Anchor | None
  输入 obs: [(digit, center_px, clipped, has_evidence)]（本帧全色检测）
  对应集: digit ∈ digit_cell 且 clipped == 0 且 has_evidence
  需 ≥5 对（≥4 才能解，但 4 对无法核验且可能退化——实测 4 对时 ground_pose 抛异常）
  RANSAC: 枚举 4 子集 → GroundHomography.solve → 内点 = 残差 ≤ ANCHOR_INLIER_PX
  输出: H / 内点集 / 逐观测残差 / 实测位姿 (x,y,θ) / 实测相机高度
  守卫: 内点 ≥4；h ∈ [25,90]cm；h_col_norm_diff 小；位姿在场内 ±1.5 格；
        ground_pose() 不抛；否则返回 None（诚实弃权）
```

**不新增核心数学**：`GroundHomography.solve / decompose / ground_pose` 全部已存在且已被
`tools/field_calib/*` 真机验证过。本轮只是在关卡层把"格心↔像素"的**对应关系来自地图**
（而不是来自人工点击）这件事接起来。

### 2.3 L2 候选核验 + 有界救援（用户 ②-a/②-b 的可执行形式）

判据不是"去掉它以后残差变小"（评审 Q5 已证明那必然成功、不构成证据），而是
**"它在共识之外"**：

1. **先做"不放弃任何观测"的假设检验**：全部对应都进 RANSAC，取最大共识。
2. **目标的候选核验**：目标数字的观测若在共识外 ⇒ **它不是真面板** ⇒ 不去压它，
   改为按锚给出的方位转向/前进（用户 ②-d），或换头部档重拍。
3. **救援（有界）**：仅当①不成立时，剔除**共识外且属于脏观测**（`clipped==1` /
   无数字证据 / 颜色歧义）的最差 1 个；**上界 = 1**（由"9 格里只剩 1 个空余格"给出）；
   **永不许剔除未裁切的干净观测**。
4. **换位复核**：同帧共识可过拟合 ⇒ 头部换档或前进一步后再验一次。
5. **次数上限 2**：救援失败 2 次即放弃本格（保护 70s/140 张/300 动作）。
6. **锚不可用（实测是常态）⇒ 不做任何核验、不改变行为**，并如实记遥测。

### 3.2 `sim/nine_grid_sim.py` 增加**同色诱饵注入**（设计完成，**本轮不实现**）

**为什么本轮不做**：实施风险评审在 `%TEMP%` 里做了原型并实测发现——
`detect_panels` 每种颜色每帧**只保留一个观测**（`main = frags[0]`，其余同色碎块
在 `:751-755` **静默丢弃**），所以一个诱饵**只有**满足下列之一才会成为"观测"：
① 它是该色**最大**的碎块（成为 `main`）；② 它与主块的间隙 ≤ `0.35×min(短边)`
且面积 ≥ `0.15×主块`（被合并）；③ 面积 > `0.35` 画幅（整色被判 `too_big` 丢弃）。
评审的原型里 3 个诱饵**把别的面板遮住**、目标色的观测**逐像素未变**（ratio 1.000）
⇒ **naive 注入什么都测不到**，做出来只会得到一个"全 0"的混淆矩阵。

**正确做法（留给专项，验收断言已定）**：诱饵规格 `{x, y, hx, hy, digit, role}`，
`role ∈ {displace, merge}`：`displace` = 比真面板更大且落在合并窗口之外（复现
"追着同色杂物跑"），`merge` = 落在窗口之内（扰动 hull/质心/裁切位）。
复用 `_draw_panel` 的 `quad()` 闭包（**提取成 `_project_quad` 共用，绝不复制**，
否则 26s/帧的退化路径会回来）。真值必须在**运行中**逐帧记录
（`stats` 是在 `run_level` 之后才组装的）。验收三条：
(a) 每个诱饵确实产出一个质心**不在任何真格心半格内**的观测（证明注入生效）；
(b) 其它颜色的真面板观测不受影响；(c) 渲染速度守卫 <0.1s/帧仍然成立。

### 8.2 ★★ WS1 yaw 精确化：**实测否证，已回退**

把 `_see_target` 的 yaw 从线性公式换成"去畸变 + atan"（数学上 0.001° 误差）：

| 臂（16 种子，实测原语） | 到达 | 拍照 | 落点中位 | 落点最大 | 超半格 |
|---|---|---|---|---|---|
| 线性（现状） | **112/112** | 2828 | 2.2cm | 4.3cm | 0 |
| 精确公式 | **72/111** | 3262 | 3.2cm | **128.0cm** | **35** |
| 精确 + 死区 15° | 35/48 | 1456 | 3.3cm | 129.6cm | 18 |
| 精确 + 死区 16° | 35/42 | 1333 | 3.2cm | 50.1cm | 11 |
| 精确 + 死区 17° | 43/48 | 1491 | 3.3cm | 33.3cm | 15 |
| （对照）线性基线同 8 种子 | **56/56** | 1418 | 2.4cm | 4.2cm | 0 |

**根因**：线性公式的 **0.734 倍率不只是死区偏移**，它是**整族 yaw 域阈值**
（死区 12° / 大转分界 30° / 变差判据 5° / 改善判据 0.5° / 小转规划下限）
共同的隐含增益标定。单独把 yaw "修准"⇒ 这族门限互相失配 ⇒ 打转 → 重搜 → 走飞。
补偿死区到 15/16/17°（对齐等效真实角度 16.3°）也救不回来。

**⇒ 处置（按用户指示"放弃具体的 yaw 数值，用简单方案"）：整套精确 yaw 机制已删除**
（`YAW_EXACT_MODEL` / `yaw_exact` / 双路遥测 / `undistortPoints` 调用全部移除），
只保留：
- `CAMERA_FOV_H_DEG` 处一段**"yaw 是伺服增益，不是角度"**的说明（含本表实测）；
- `tests/test_nine_grid_yaw.py` 改为**纯数学增益闸**：钉住 0.734、钉住"名义 FOV ≠
  真实 FOV"、并**禁止把精确公式重新接回控制路径**（含源码级断言）。

### 8.7 ⚠️ WS6 的结论**被用户纠正，作废重来**：测错了组合

**用户澄清了四个概念，它们不能混为一谈：**

| 概念 | 含义 |
|---|---|
| **老办法** | 二值：对准了就直行 / 没对准就转 |
| **三档分区** | 看目标落在画面哪个区域 → 直行 / 横移 / 旋转 |
| **三阶段** | 对准 → 接近 → 到达，三段各有各的切换判据（12° 死区 / 框宽 920px / 色占比回落） |
| **统一决策** | 不分三段，用同一套逻辑一路走到目标 |

用户提的方案是 **三档分区 ＋ 统一决策**。
而 §8.7 上一版测的是 **三档分区塞进三阶段**——用户自己就说了这个组合当然不好。
⇒ **上一版"不再需要三档分区"的结论不成立，已撤销。**

**但那次测量给出的两条观测仍然有效，且含义要重新解读：**

1. 三臂都 112/112、分区臂多花 3~6% 拍照 ⇒ 说明**在三阶段骨架里**分区律是纯开销。
2. **"APPROACH 段旋转档出现 0 次"是三阶段的产物，不是分区律的性质**：
   三阶段里 ALIGN 段已经把 |yaw| 压进死区，APPROACH 自然用不到旋转档。
   **统一决策下没有预对准**，旋转档在近距离会真的被用到——这正是蓝档要防的事
   （近距离一步旋转 ≈ 9.8cm > 开关半宽 5.5cm，精度只能靠厘米级横移）。

⇒ **正确待办**：把"三档分区 + 统一决策"作为一个**独立实验**实现并 A/B：
用一个循环替换 `_seek_align_approach` → `_arrive_visual` 的分段调用链，
每帧按 `_zone_of(yaw, near)` 决定直行/横移/旋转，到达判据沿用（色占比回落 / 前压兜底），

### 8.8 WS7 新增两个真机计时脚本（用户手动运行）

| 脚本 | 量什么 | 性质 |
|---|---|---|
| `tools/measure_frame_cost.py` | 单帧各环节：拍照 / 色占比 / **单色**检测 / **全色**检测 / 锚解算；并折算"现状 / +WS4 / 统一决策"三种口径的**每帧开销**与单格可拍帧数 | **只拍照 + 纯计算**，不发动作、不动舵机 |
| `tools/measure_anchor_cost.py` | 锚解算耗时 **vs 对应点数**（RANSAC 枚举 4 子集）的曲线与最坏情况；折算"每帧解一次锚"占单格预算的比例 | 同上 |

**为什么需要**：WS4 与"统一决策"都要在**每帧**多做一次全色检测，
而真机算力从未实测；仿真里拍照/计算是瞬时的，**测不出这件事**。
（实测后更正：全色检测只是单色的 **1.8×**，不是最初假设的 ≈7×。）

运行方式（PC，先把仓库同步到机器人）：
```powershell
python tools/sync_to_robot.py
python tools/exec_on_robot.py --cmd "cd /home/pi/Robot_Competition && /home/pi/jupyter-env/bin/python3 tools/measure_frame_cost.py" --timeout 900
python tools/exec_on_robot.py --cmd "cd /home/pi/Robot_Competition && /home/pi/jupyter-env/bin/python3 tools/measure_anchor_cost.py" --timeout 900
```

**判读**：单格 70s 预算下若两脚本合计仍能拍够 ~40 帧，则统一决策在算力上可行；
WS4 的默认值也按同一数字决定（目前 `VIS_ARRIVE_ANCHOR_ENABLED = False`）。

**★ 实测结果（2026-09-24，RPi5 上跑出）**

| 环节 | 最小 | 均值 |
|---|---|---|
| 拍照（fswebcam + 读图） | 0.540s | **0.572s** |
| 色占比 color_ratio（单色） | 0.043s | 0.043s |
| detect_panels 单色 | 0.050s | 0.051s |
| **detect_panels 全 7 色** | 0.089s | **0.090s** |
| 锚解算（10 个对应点） | 0.040s | 0.040s |

锚解算 **vs 对应点数**（RANSAC 枚举 4 子集，上限 80）：

| N | 4 子集数 | 实际枚举 | 均值 |
|---|---|---|---|
| 5 | 5 | 5 | 0.0026s |
| 6 | 15 | 15 | 0.0075s |
| 7 | 35 | 35 | 0.0173s |
| 8 | 70 | 70 | 0.0391s |
| 9~12 | 126~495 | **80（封顶）** | **0.0396~0.0405s** |

**⇒ 三条结论（其中一条更正了此前的假设）：**

1. **更正**：全色检测只是单色的 **1.8×**，**不是此前写的 ≈7×**。
   原因是公共开销（降采样 2592→1296、光照归一化、BGR→HSV）占大头，
   7 个颜色掩膜本身很便宜。**此前"每帧全色检测代价高"的判断是错的。**
2. **算力不是瓶颈**：单格 70s 可拍 **98~110 帧**，而实际单格最多 ~40 张；
   拍照本身占每帧 **90%**（0.572 / 0.633），感知计算只占 10%。
   - 现状每帧 0.633s → 单格 110.6 帧
   - +WS4（每 3 帧一次全色+锚）每帧 0.676s → 103.5 帧
   - **统一决策（每帧全色+锚）每帧 0.712s → 98.3 帧**
3. **锚解算在 80 子集处封顶**，对应点数 9→12 耗时不变（0.040s）；
   统一决策每帧解一次锚、单格 ~40 帧合计 **1.6s ≈ 单格预算的 2%**。

⇒ **WS4 的"算力未实测"这条阻塞理由已解除**；它的默认值现在只剩"效果"一个判据
（112/112 不变、动作 −29、落点中位 2.2→2.0cm、最大 4.3→5.9cm ⇒ 仍在噪声内，
故维持 `False`）。**统一决策在算力上确认可行**，成为下一轮的第一优先。
