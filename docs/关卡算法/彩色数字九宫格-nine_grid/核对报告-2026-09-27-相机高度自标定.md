# 布局扫自标定与"相机高度"的核对报告（2026-09-27）

> 缘起：有 agent 提出「布局扫是在 (安装偏移, 相机高度) 参数网格上投票解格阵的
> （`levels/nine_grid_shared.py:1289-1298`）。真实高度 33.9cm 落在搜索范围
> 36~70 之外 ⇒ 这个自标定在设计上就永远找不到正确答案，最多顶到 36.0
> （离真值差 2.1cm），而且"36"这个下界本身也是拿错的高度写出来的。」
>
> 本报告用**现场真实照片 + 真实代码路径**把这句话逐条核对了一遍。结论：
> 现象说对了，"最多顶到 36.0、只差 2.1cm"是错的（差 14.6cm），而且**改下界救不回来**。

## 0. 结论速览

| 断言 | 核对结果 | 证据 |
|---|---|---|
| 自标定是在 (安装偏移, 相机高度) 网格上投票解格阵 | **成立** | `_fit_grid` L1370-1415；本次实测 10 个组合投票，全部解出正确布局 |
| 33.9cm 落在搜索范围 36~70 之外 | **成立** | `LAYOUT_SCAN_HEIGHT_MIN_CM = 36.0`（`:327`）> 33.9 |
| 因此"永远找不到正确答案" | **成立，但原因不是下界** | 把下界降到 25cm，结果只从 48.5 → 47.5cm（见 §3） |
| "最多顶到 36.0，离真值差 2.1cm" | **错** | 实测自标定报 **48.5cm**，与卷尺标定 33.93 差 **14.6cm（+43%）** |
| "36 这个下界是拿错的高度写出来的" | **无法证实 / 很可能是反的** | 36 与 70 都不对应任何已知测量值；真正被"拿错的高度"污染的是 `camera_config.CAM_HEIGHT_STANDING_CM = 56.0` |

**真正的病根有两条，都不在搜索范围上：**

1. **观测质量**：本次照片 53 条观测里 **36 条被画幅裁切**（数字 7 只有裁切观测）。
   裁切质心偏差实测 1.3~8.4cm，把格阵的"33.3cm 刚性"糊掉了。合成实验证明：
   观测一旦干净，同一套代码能把真值**精确到 0.0cm** 解回来（§2）。
2. **像素域精修没通过**：`calibrate_pixel_pose` 是唯一能让连续高度逃出网格步长的
   机制，现场报"格心重投影残差中位 **78.8px** > 40px"未收敛 ⇒ 高度直接由
   网格票的中位数定格 ⇒ 于是"下界 + 5cm 步长"这两个离散化选择**替**算法做了决定。

[diag] 拟合: cells={1: 8, 2: 5, 3: 4, 4: 6, 5: 3, 6: 0, 7: 1}   ← 与照片读图真值一致 ✓

[diag] 自标定: 安装偏移 +30.0° / 高度 48cm；刚体残差 5.7cm

要点：**布局是对的，常数是错的**。这正是最危险的组合——`digit_cell` 正确，
`_pitch_offset_deg / _cam_height_cm` 悄悄偏了 43%，日志里却写"标定结果"。

## 2. 合成实验：把"搜索范围"这个变量隔离掉（`tools/exp_synthetic_identifiability.py`）

用同一套投影代码生成**无噪声**观测（站位/头部档/可见性与现场同量级），跑真实的
`_fit_grid`：

```
  真值高度  真值偏移  观测数  解出布局  解出高度  解出偏移   RMS
      33.9     +25.0      16   ✓          33.9     +25.0  0.00cm
      36.0     +21.3      18   ✓          36.0     +21.3  0.00cm
      48.0     +21.3      20   ✓          48.0     +21.3  0.00cm
```

**33.9cm 明明在网格 [36,70] 之外，却被精确解了出来**——因为
`calibrate_pixel_pose`（`:390`）是连续优化、界是 `25.0 ≤ h ≤ 100.0`（`:472`），
网格只提供初值。把下界改成 30cm 后仍是 33.90cm（RMS 0.00cm）。

**同一个脚本加噪声后：**

```
  真值高度  偏差幅度  解出高度  解出偏移
      33.9     1.0cm      34.0     +21.1
      33.9     3.0c   ✗ 拟合失败（参数网格投票不足（得票 9/9，次高得票 []））
      48.0     3.0cm      51.0     +25.0   ← 被推到网格点，且"未精修"
```

⇒ **这套自标定对观测质量极其敏感**：1cm 量级的位置偏差它还能扛，3cm 就崩。
现场恰恰是 3~8cm 量级的裁切质心偏差。

## 3. 真照片上的投票明细（`tools/exp_vote_detail.py`）

```
== 现状网格 高度[36,70] 步5 ==
  成功组合 10 个；其中解出 = 照片真值 的 10 个
   高度   成功组合
   36.0          1      41.0  2      46.0  2      51.0  2      56.0  2      61.0  1
```

**票均匀撒在 36~61cm 上，每张票都给出同一个（正确的）布局。**
布局对高度不敏感 ⇒ 高度的最终取值是被"下界/步长/中位数"这些离散化选择决定的，
不是被数据决定的。把 33.9 塞进网格：33.9 那一档**一票都拿不到**
（成功组合从 38.9 起）。细网格（步 1cm）同样是 53 个组合全票通过、全在 36~64。
⇒ **真照片里的信息量不足以支持 33.9；改下界不会改变任何结论。**

## 4. 33.9cm 这个数本身可信吗？

- 来源：`tools/calib_ruler_profile.py` → `.worktrees/stairs/archive/result/ruler_profile.json`
  （14 个卷尺刻度 3~60cm，含畸变物理模型 **RMS 2.72px**）
  `h_eff = 32.73cm`（光心到刻度平面）+ 卷尺厚 1.20 = **33.93cm**。
  该文件另给 `theta_deg = 55.11°`；按本工程约定（`ground_homography.from_pose`：
  有效俯角 = `(1500-pitch)*0.09 + offset`，法线角 = 90° − 俯角）换算，
  pitch1100 的有效俯角 ≈ 57.3° ⇒ 安装偏移 ≈ +21.3°，与 `stairs_hurdle.py:25`
  写的「pitch 1100、光心离地 33.9cm、安装下俯偏移 19.1°」在 2° 内自洽。
  **这是一个完整、内部一致的直接测量，可信度高于任何自标定输出。**
- 反证它的唯一证据是布局扫的 48.5cm——而那一版的像素残差是 78.8px，
  它自己都报"未收敛"。
- ⚠️ 时间线：照片是 2026-09-11 拍的（pitch 1200/1040），卷尺标定是 2026-09-25，
  舵机在 2026-09-27 换过（pitch 1040 → 1100）。高度只与机械安装有关，
  换舵机不改光心高度，所以 33.9 仍适用于当前机器；但**偏移会随舵机改**，
  所以只能把 33.9 当"高度常量"，不能把 21.3° 当"当前偏移"。
- 未验证项（需要现场 5 分钟）：机器人行驶面与面板所在面是否同一平面。
  若机器人在地面、面板在抬高的台面上，则"相机离地 33.9"与投影模型假定的
  "相机到面板平面 33.9"不是一回事，必须按 `h − 台面高` 修正。

## 5. 影响面（43% 尺度误差会伤到什么）

| 用到 `_cam_height_cm` 的地方 | 影响 |
|---|---|
| 导航选方向 / 到达判决 | **无**：统一决策与三段式的导航都不读 `digit_cell`/位姿，到达靠视觉闭环（`VIS_ARRIVE_*`） |
| 可见地面带 / "面板四角完整可见窗口" 的推算 | **错**：按 48.5 推的 15~36cm 窗口是按 33.9 推的 1.43 倍 |
| `_reanchor_pose` 反推位姿、`_arena_guard` 离场护栏 | **错**：死推位姿的尺度偏大 43%，护栏/搜索预算的判断随之偏 |
| `GN_PIXEL_GATE` 定位门 | 残差本已 78.8px，定位风暴与"拍照数爆表"的历史现象与此一致 |
| `tests/test_nine_grid_replay.py:69` | `assert 35.0 <= _cam_height_cm <= 70.0` —— **把错误区间钉进了 CI**，48.5 顺利通过 |

## 6. 怎么改（按性价比排序）

### P0 · 让常数有唯一真源，别再让自标定独占写权限

```python
# core/camera_config.py（或 nine_grid 本地）
CAM_HEIGHT_MEASURED_CM = 33.9   # 卷尺标定（tools/calib_ruler_profile.py 产物）
                                # 只写实测值；自标定不许覆盖它，只许"核对"
```
- `layout_scan` 写回 `self._cam_height_cm` 的条件收紧为：
  **仅当 `calibrate_pixel_pose` 收敛（`med_px ≤ PIXEL_CALIB_MED_MAX_PX`）才采信**；
  否则用 `CAM_HEIGHT_MEASURED_CM`，并打印 `[布局] 相机高度自标定未通过像素门
  （中位 XXpx），采用实测高度 33.9cm`。
- 这样即使现场光照再差，最坏情况也只是"高度回到实测值"，
  而不是"回到一个网格点上的随机数"。

### P0 · 高度搜索范围：围绕实测值放宽，而不是固定 36~70

```python
LAYOUT_SCAN_HEIGHT_MIN_CM = 24.0        # 33.9 之外仍留裕量（换机器人/换装配）
LAYOUT_SCAN_HEIGHT_MAX_CM = 70.0
LAYOUT_SCAN_HEIGHT_STEP_CM = 2.0        # 5cm 步长 = 高度分辨率 ±2.5cm，太粗
LAYOUT_SCAN_DEFAULT_HEIGHT_CM = 33.9    # 实测缺省（初值/回退）
```
代价：组合数 10×21×15 = 3150，`_aggregate` 每次 ~0.3ms、`assign_grid_cells`
只在 7 个数字齐了才跑 ⇒ 量级仍是秒级（现状 10×8=120 组已是秒级）。
若担心现场耗时，可先粗扫（步 5）定布局、再在胜出点附近细扫（步 1）定常数。

### P1 · 修"高度不可辨识"的根：同档俯仰的退化

`_fit_grid` 已经自己警告过：「仅单档俯仰有观测：安装偏移与名义俯仰角退化」。
本次照片 10 帧里确实只有 pitch 1200/1040 两档，但 1040 的观测几乎全被裁切。
**把 `calibrate_pixel_pose` 的参数化从"每档各自的 (偏移, 高度)"改成"共享一个
高度 h、每档一个偏移"**，两档观测一起解。合成实验（`exp_synthetic_identifiability.py`）
显示：加上第二档后，h 与偏移都能精确解出，且不再触发退化警告。

### P1 · 修观测质量（这是 43% 误差的真正来源）

- 53 条里 36 条裁切、数字 7 **全部**裁切。布局扫应尽量只用"四角完整可见"的观测
  定常数（`LAYOUT_SCAN_MIN_CLEAN_DIGITS = 6` 已有这个思路，但门槛没落到常数上）。
- 建议加一条廉价的自检：拿解出的常数**预投**每个完整可见面板的色块像素边长
  （物理边长 28cm，`PANEL_HALF_CM=14.0`），比值偏离 1.0 超过 15% 就告警——
  这是一把与相机高度**无关的绝对尺**，理论上能一次性打破 (偏移, 高度) 退化谷。
  （本次数据里可用样本太少、同色杂物污染严重，只做告警不做定权，见
  `tools/exp_height_floor_and_scale.py` 的散点。）
- 现场协议：布局扫前把机器人放到"所有面板都在画幅内"的站位（这条已经写在
  `.worktrees/nine_grid_elegant/levels/nine_grid_shared.py:113-116` 的实测窗口里）。

### P2 · 清理被这个 bug 带出来的陈旧物

- `core/camera_config.py`：`CAM_HEIGHT_STANDING_CM = 56.0` 的注释
  "双帧拟合 ≈56" 应标注**这是退化谷上的一个点，不是独立测量**；九宫格侧改用
  本地常量（`.worktrees/nine_grid_elegant` 已经这么做了）。
- `tests/test_nine_grid_replay.py:69`：`assert 35.0 <= h <= 70.0` 改成
  "自标定高度必须与实测高度相差 ≤20%，或像素门未通过时等于实测高度"，
  否则 CI 会继续为错误常数背书。
- `levels/nine_grid_shared.py:393-397` 的注释「高度差 3cm 会让 GN 残差从 <1px
  涨到 16~23px」只对 sim 成立；真照片上 43% 的高度误差对应的中位像素残差是
  **78.8px**，`PIXEL_CALIB_MED_MAX_PX = 40` 这道门拦不住它——门该收紧或
  改成"相对最优残差"的形式。

   （pitch1100 档）；而 pitch1200 档按旧照片更像是 +8~13°。换过舵机之后
   偏移必须**重新标定**，本次只把高度锚死了。
2. **`REJECT_CALIB_HEIGHT_BAND_CM = 8.0` 是拍的**：依据是"本夹具精修给出 41.8cm
   （离实测 7.9cm）而像素代价面在 34~58cm 上是平的"。若换了相机/机器人，
   这个带要跟着实测重定。
3. **平面假设未验证**：33.9cm 是"光心离**机器人行驶的那块地面**"；若面板在
   抬高的台面上，投影模型要的是"光心到**面板所在平面**"的距离，得按
   `h − 台面高` 修正（`LAYOUT_SCAN_HEIGHT_OFFSETS_CM` 的 +5/+9 两档就是为这种
   不确定性留的松弛，但那只影响布局投票，不影响写回的常数）。
4. **仿真侧行为会变**：`CAM_HEIGHT=33.9` 之后，同一 seed 的无头仿真从"7/7 到位"
   变成"面板1 磨 12 次后被离场护栏终止"。A/B 实测：
   `NINEGRID_CAM_HEIGHT_CM=56 python -m sim.nine_grid_sim --no-ui --seed 3` → 7/7 到位；
   缺省（33.9）→ 卡在面板1。**这不是导航逻辑回归**（导航不读这两个常数，
   audit 工具验证渲染与投影仍严格同源），而是"仿真世界的高度"整体降了 39%：
   可见地面带、遮挡、落点全都变了，而关卡里那批按 56cm 世界调出来的
   搜索/对准参数没有跟着改。**上实机前不要用仿真结论外推**；反过来，
   真机的真实高度就是 33.9，这条仿真差异不影响真机。
