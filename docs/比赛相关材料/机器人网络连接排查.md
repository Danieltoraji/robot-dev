## 案例 1:WiFi 省电模式(2026-09-05)

## 1. 现象

- PC 访问机器人 Jupyter（http://192.168.31.209:8888）频繁超时，时好时坏；
- PC `ping` 机器人**丢包 ~53%**（15 发 7 收）；
- 此前所有依赖网络的操作（代码同步、远程执行、照片拉取）随机失败。

## 2. 根因

**树莓派 WiFi 省电模式（NetworkManager 默认开启 powersave）**：
无线电在空闲时休眠，**入站**包（PC→机器人的 ping/HTTP）被睡过去的网卡丢弃；
而机器人**主动出站**的流量会唤醒 radio，所以"机器人 ping 网关 0% 丢包、
PC ping 机器人 53% 丢包"这种不对称是本问题的指纹。

排除项（排查时已验证正常，复发时先复查）：
- 射频信号：`-51 dBm`（很强，弱信号一般 -70 以下）；
- 驱动：`dmesg` 中 brcmfmac 初始化无异常；
- 机器人→网关链路：0% 丢包、RTT ~6ms。

## 3. 诊断命令（按顺序）

```bash
# PC 侧：量化丢包
ping -n 15 192.168.31.209

# 机器人侧（Jupyter 终端或 exec_on_robot）：
iw dev wlan0 link                 # 信号强度/速率（-50s 很好，-70 以下查射频）
iw dev wlan0 get power_save       # ★ 省电模式状态（本案元凶）
ip addr show wlan0 | grep inet    # 确认 IP
ping -c 8 192.168.31.1            # 机器人→网关：0% 丢包说明射频链路正常
dmesg | grep -iE 'wlan0|brcmfmac' | tail   # 驱动日志
```

不对称判据：**机器人→网关丢包低 + PC→机器人丢包高 = 入站被省电吞掉**；
两个方向都高 = 射频/干扰问题（查距离、2.4G 拥挤、USB3 设备干扰）。

## 4. 修复（2026-09-05 已实施）

```bash
# 运行时立即生效（重启后失效）：
sudo iw dev wlan0 set power_save off

# 持久化（NetworkManager 配置，重启后依然禁用）：
sudo bash -c 'mkdir -p /etc/NetworkManager/conf.d && printf "[connection]\nwifi.powersave = 2\n" > /etc/NetworkManager/conf.d/wifi-powersave-off.conf'
```

- 配置文件：`/etc/NetworkManager/conf.d/wifi-powersave-off.conf`
  （`wifi.powersave = 2` = 禁用省电）；
- 修复验证：PC ping 15 发 **15 收，0% 丢失**（修复前 53%）。

## 5. 附带保险（PC 端工具已内置）

`tools/sync_to_robot.py`、`tools/pull_from_robot.py`、`tools/exec_on_robot.py`
的登录与请求均已加**链路抖动重试**（3 次退避），偶发超时自动恢复，
无需人工重跑。

## 6. 若复发，按此顺序查

1. `iw dev wlan0 get power_save` —— 是否仍是 off（换镜像/重装系统后会重置）；
2. 信号强度是否仍在 -60 以上（场地变了就挪路由器/加天线）；
3. 两个方向都丢包 → 射频干扰（2.4G 拥挤、USB3 设备靠近天线、路由器漫游）；
4. IP 是 DHCP 动态分配——**建议在路由器上为机器人做 IP 保留**（当前 192.168.31.209），
   防止换网络环境后 IP 变化导致连不上；

## 7. 案例 2：开机连错路由器（2026-09-07）

### 现象

- PC ping 机器人 4 发全部"无法访问目标主机"（ARP 层失败，**不是**超时丢包）；
- 全网段扫描（254 IP）：无任何树莓派 MAC 在线、无任何主机开 8888 —— 机器人不在
  192.168.31.x 的任何角落；
- 排查中 209 偶尔闪现（26% 丢 → 一度 10/10 全通 → 又消失）；
- 机器人侧实况：09:54 开机，**09:53 起关联的是 `eelab901b_2`（AP 48:5f:08:9e:44:a1），
  10:26 才切到 `eelab901b`（主路由 AP 44:f7:70:b0:13:c6，与 PC 网关同机）**，之后 0% 丢包稳定。

### 根因

实验室有**两台路由器**：主路由 `eelab901b` 和副路由 `eelab901b_2`（小米默认网段都是
192.168.31.x，但两台互相独立、广播域隔离）。机器人存的 3 个 WiFi 配置
（`eelab901b` / `eelab901b_2` / `eelab901b_5g`）autoconnect 全开、优先级相同，
开机连上 `_2` 就进入 PC 看不见的隔离网络；期间漫游切换的几秒造成"闪现"。
次因：当天机器人 09:54 才开机，开机前的"连不上"是正常的。

Jupyter 是 systemd 服务 `jupyter.service`（开机自启），只要机器人上线服务就在。

### 排查指纹与命令

```bash
# PC 侧："无法访问目标主机" = ARP 失败 → 设备不在这个广播域（对比：超时 = 案例 1）
arp -a | grep 192.168.31.209        # 连 ping 都"通"却查无此 MAC → 别信 ping，看 ARP

# 机器人侧（趁闪现窗口或恢复后）：
iw dev wlan0 link                   # 看 Connected to 的 AP MAC 和 SSID 是否主路由
journalctl --no-pager | grep -E "Associated|Trying to associate" | tail
nmcli -f NAME,TYPE,AUTOCONNECT,ACTIVE connection show
```

### 修复（待实施，二选一或都做）

```bash
# 提高主路由优先级（推荐：不影响比赛时连其他 AP）：
nmcli connection modify 'eelab901b' connection.autoconnect-priority 100
# 或直接禁掉副路由自动连接：
nmcli connection modify 'eelab901b_2' connection.autoconnect no
```

根治仍推荐 §6.4 的路由器 IP 保留 + 固定连主路由。
