## 1. 审查目标与判定标准

依据需求，给出四条可执行的判定标准：

1. **基础能力归 core**：定位、动作执行、头部舵机、几何工具等「所有关卡都能复用」的能力放在 core。
2. **关卡内容归 level**：赛道数据（tag 坐标、墙壁、路点）、导航决策、关卡专用阈值放在关卡文件。
3. **core 宁少勿多**：core 不出现「只服务于某类关卡决策」的东西；core 里每一个符号都必须**被 core 自己用到**或有明确的复用理由。
4. **无跨关卡混乱**：同一个概念（如「朝向阈值」「停靠时间」）只能有**一个权威来源**；不同关卡之间互不感知、互不影响。

## 2. 现状梳理：三层结构与职责

| 层 | 文件 | 当前实际提供的内容 |
|----|------|-------------------|
| 入口 | `main.py` | `LEVELS` 注册表（目前仅 goodluck）、`RobotState` 装配、关卡分发 |
| 核心 | `core/robot_core.py` | `RobotState` 类（run_action / set_head / capture_image / capture_frame / detect_apriltag / solve_pnp / compensate_head_offset / locate_with_scan / locate_with_retry）、几何工具 `distance_point_to_rect`、相机内参、头部舵机常量 |
| 视觉能力 | `vision/` | 检测器（LineDetector / ColorBlobDetector / DigitRecognizer / YoloDetector）+ 数据模型 + 统一接口（关卡按需选用，见 `docs/视觉能力/`） |
| 关卡 | `levels/goodluck.py` | `tag_poses`、`WALLS`、`ROUTE`、决策阈值、动作参数、导航算法、避障、`run_level` |
| 模拟 | `sim/goodluck_sim.py` | `SimState`、`Visualizer`、`SimRobotState(RobotState)`、噪声配置、`run_simulation` |

**依赖方向（理想）**：`main → level → core`，`sim → level + core`。
**依赖方向（实际）**：符合理想方向，但 `sim` 是「硬编码 import goodluck」而非「按关卡名选择」，见 3.4。

## 3. 逐项审查结果

### 3.1 做得对的地方（符合预期 ✅）

1. **`tag_poses` 依赖注入**：`RobotState.__init__(tag_poses)` 让关卡把「标签世界坐标」注入 core，而不是 core 里写死某关卡的坐标。这是最关键、最正确的解耦点。
2. **几何工具分层干净**：纯几何 `distance_point_to_rect` 放 core（关卡无关）；依赖 `WALLS` 的 `distance_to_walls` 放 level（关卡相关）。分界准确。
3. **硬件导入隔离**：hiwonder / apriltag / cv2 全部 try/except，PC 无硬件也能 import，模拟器通过继承重写 I/O，不触真机。
4. **模拟器用「继承 + 重写」而非 monkey-patch**：`SimRobotState` 只重写 `run_action / solve_pnp / set_head` 三个 I/O 方法，算法零改动即可仿真。
5. **关卡复用 core 常量**：`levels/goodluck.py` 正确地从 core 导入 `RobotState, distance_point_to_rect, HEAD_CENTER`，说明关卡知道「头部中位」这类硬件常量该向 core 要。
6. **`RobotState` 类方法本身关卡无关**：9 个公开方法都不引用 `WALLS` / `ROUTE` / 具体 tag ID，API 面是干净的。

### 3.2 问题 P1（中）：core 存在「冗余决策常量」，造成双重真相 ✅ 已修复（见 §5）

`core/robot_core.py` L59–L64 定义了 6 个常量，但**只有 `MAX_LOCATE_RETRIES` 被 core 用到**（`locate_with_retry` L292–L293）。其余 5 个在 core 内是「死代码」：

| 常量 | core 中定义值 | core 是否使用 | levels/goodluck.py 是否重复定义 | 关卡中定义值 |
|------|--------------|--------------|-------------------------------|-------------|
| `ORIENTATION_THRESHOLD` | 0.26 | ❌ 未用 | ✅ 重复 | 0.26 |
| `POSITION_THRESHOLD` | 3.0 | ❌ 未用 | ✅ 重复 | 3.0 |
| `STOP_TIME` | **3** | ❌ 未用 | ✅ 重复 | **0.1** ⚠️ |
| `OBSTACLE_THRESHOLD` | 15.0 | ❌ 未用 | ✅ 重复 | 15.0 |
| `SAFE_MARGIN_CM` | 3.0 | ❌ 未用 | ✅ 重复 | 3.0 |
| `MAX_LOCATE_RETRIES` | 5 | ✅ 使用 | ❌ 不重复 | — |

**危害**：
- 「朝向阈值」「停靠时间」这类**决策参数**本应归关卡所有（不同关卡障碍布局不同、要求不同），但 core 里残留了一份拷贝，形成**两个权威来源**。
- `STOP_TIME` 已经出现**值不一致**（core=3 秒，关卡=0.1 秒）——这正是「跨关卡混乱」的现成案例：未来维护者会分不清该改哪一份，甚至误改 core 那份（反正它不影响任何行为，改了也不报错）。
- 违反「core 宁少勿多」：core 里放了 5 个自己不消费的符号。

> 方向判断：`levels/goodluck.py` **自己定义决策常量**是正确的（关卡自治），问题在于 core 没删干净那 5 个遗留副本。**已修复**：5 个死常量已删除，仅保留 `MAX_LOCATE_RETRIES`；`STOP_TIME` 统一为关卡侧持有（当时改回比赛值 3 秒，2026-08-30 提速后当前为 0）。

### 3.3 问题 P2（低）：core 存在几处「关卡无关但被写死」的假设 ⚠️

这些不是「关卡逻辑泄漏」，而是 core 把「本应可配置」的东西写死了，多关卡时可能被迫改 core：

| 位置 | 硬编码内容 | 多关卡风险 |
|------|-----------|-----------|
| `detect_apriltag`（core L191） | `families="tag36h11"` 写死 | 若另一关卡用别的 tag 家族（如 tagStandard41h12），必须改 core 或加参数 |
| `locate_with_retry`（core L299/302） | 动作名 `turn_left_small_step` / `turn_right_small_step` 写死 | 假设动作库里一定有这两个动作组；换平台/换动作名会失效 |
| `capture_image`（core L173） | 输出路径 `/home/pi/Pictures/photo_*.jpg` 写死 | 属环境假设，跨机/跨关卡可能需改 |

> 判定：这些属于「core 对运行环境/视觉方案的**隐式假设**」，建议参数化或至少文档化。其中 tag 家族是唯一可能「随关卡变化」的，优先级相对高。

### 3.4 问题 P3（高）：模拟器硬绑定 goodluck 关卡 ❌

`sim/goodluck_sim.py` 通过 `from levels import goodluck as gl`（L43）**硬编码**了关卡，并在全文直接引用 `gl.WALLS / gl.ROUTE / gl.tag_poses / gl.run_level / gl.FORWARD_ONE_STEP_CM / gl.TURN_*` 等：

```
sim/goodluck_sim.py 中对 gl.* 的直接引用（共 20+ 处）：
  L217/220/223   gl.CAMERA_FORWARD_OFFSET_CM / TURN_LEFT_RADIUS_CM / TURN_RIGHT_RADIUS_CM
  L273/281/294   gl.WALLS / gl.ROUTE / gl.tag_poses
  L432~453       gl.FORWARD_ONE_STEP_CM / BACK_FAST_CM / LEFT_MOVE_CM / TURN_* ...
  L580/586       gl.tag_poses / gl.run_level
```

**危害**：`main.py` 已经用 `LEVELS` 注册表实现了「按关卡名分发」，但模拟器**绕过了这个注册表**，写死 goodluck。新增关卡后，模拟器无法 `python -m sim.goodluck_sim new_level` 直接仿真新关卡，必须复制改造模拟器或给它硬加分支——这就是典型的「跨关卡扩展阻塞」。

**它其实是同一个核心问题的另一面**：模拟器需要知道「当前关卡的赛道数据 + 动作参数 + run_level」，但它没有像 `main.py` 那样通过关卡名去查注册表，而是 import 具体关卡模块。

### 3.5 边界讨论：导航决策该归 core 还是 level？

这是本项目最容易纠结的点，给出明确建议：

| 内容 | 现状 | 建议归属 | 理由 |
|------|------|---------|------|
| 定位（PnP、头部扫描、重试） | core | **core** ✅ | 纯硬件/视觉能力，所有关卡完全复用 |
| 几何（点到矩形距离） | core | **core** ✅ | 关卡无关纯函数 |
| 动作执行 / 头部舵机 | core | **core** ✅ | 硬件 I/O |
| 贪心平移 / 转向 / 避障过滤 | level | **level** ✅ | 依赖本关卡 `WALLS`、动作步长、阈值 |
| `distance_to_walls` | level | **level** ✅ | 依赖本关卡 `WALLS` |
| 路点表 / 停靠点 | level | **level** ✅ | 关卡规划内容 |

**结论**：当前把「导航决策」全部放在 `levels/goodluck.py` 是**符合「core 宁少勿多」**的——即便未来多个关卡都用「路点 + 避障 + 贪心平移」的套路，宁可让关卡之间**少量重复**导航代码，也不要把一个「还只有单关卡实例、尚未提炼出稳定接口」的导航引擎过早塞进 core。**过早抽象比少量重复更危险**，这也契合「宁少勿多」。

> 例外：若后续出现 3+ 个关卡共享**完全相同的**导航算法、只是数据不同，那时再把导航引擎提升进 core（并让关卡注入 `WALLS / ROUTE / action_params`）才是合理的重构时机。

## 5. 修复建议（按优先级）

### ✅ 已完成｜优先级 1：删除 core 中的冗余决策常量（消除双重真相）

把 `core/robot_core.py` L60–L64 中的 5 个常量**删除**，只保留 core 真正使用的 `MAX_LOCATE_RETRIES`：

```python
# core/robot_core.py 只保留：
MAX_LOCATE_RETRIES = 5   # 定位失败最大重试次数（locate_with_retry 使用）
# 删除：ORIENTATION_THRESHOLD / POSITION_THRESHOLD / STOP_TIME / OBSTACLE_THRESHOLD / SAFE_MARGIN_CM
```

- 决策参数统一由 `levels/goodluck.py` 持有（它已经在定义了，无需改动关卡侧）。
- 同时修正 `STOP_TIME`：确认关卡侧 `0.1` 是测试值后改回比赛要求的 `3`（当时已完成；2026-08-30 提速后当前为 `0`，需要恢复停靠再改回 `3`）。
- 影响面：core 删死代码不影响任何行为；模拟器/关卡不引用 core 的这些常量，零破坏。

### 🔴 优先级 2：模拟器按关卡名分发，复用 LEVELS 注册表

把 `sim/goodluck_sim.py` 的 `from levels import goodluck as gl` 改为按参数选择关卡，与 `main.py` 保持一致：

```python
# 方案：main.py 导出 LEVELS（或 sim 复用同一注册表）
from main import LEVELS            # 或新建 levels/__init__.py 暴露 registry
level = LEVELS.get(level_name, LEVELS["goodluck"])
```

- 把全文 `gl.WALLS / gl.ROUTE / gl.tag_poses / gl.run_level / gl.FORWARD_*` 改为从选中的 `level` 模块取。
- 新增关卡时：只需在 `LEVELS` 注册，`python -m sim.goodluck_sim new_level` 即可仿真，无需改模拟器。
- 建议：把注册表从 `main.py` 抽到一个无副作用模块（如 `levels/registry.py`），避免 `import main` 触发入口逻辑。

### 🟡 优先级 3：参数化 core 的视觉/环境假设

```python
# detect_apriltag 增加 tag_family 参数，默认 tag36h11
def detect_apriltag(self, filename, families="tag36h11"): ...

# capture_image 增加输出目录参数
def capture_image(self, output_dir="/home/pi/Pictures"): ...

# locate_with_retry 的动作名改为可配置/常量，集中声明 core 对动作库的假设
```
若短期内不参数化，至少在上方文档注释里**显式声明**「core 假设：动作库含 turn_left_small_step / turn_right_small_step；视觉采用 tag36h11；照片输出目录为 …」，把隐式假设显式化。

### 🟢 优先级 4（可选）：`MAX_LOCATE_RETRIES` 收敛为可覆盖默认值

`MAX_LOCATE_RETRIES` 是「定位策略」参数，理论上不同关卡（光照/环境不同）可能想覆盖。可保留为 core 默认值，并允许关卡传入，但**不强制**——单关卡阶段保持现状即可。
